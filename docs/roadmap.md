# ii — дорожная карта

> Этот документ — на русском для удобства планирования. Весь код и остальная документация — на английском.

Принцип: **вертикальные срезы**. Каждый этап заканчивается работающим, протестированным и измеренным результатом,
который можно показать через CLI `ii`. Архитектурные «швы» (Backend API, домены памяти, планировщик, state-значения,
символьные формы, правила градиентов в OpSchema) закладываются с первого этапа, даже если реализация за ними пока
простая, — чтобы позже не переписывать ядро.

**Кроссплатформенность с этапа 0**: Windows, Linux, macOS (tier 1) собираются и проходят все тесты в CI на каждом
коммите. Android подключается на этапе 2 (вместе с NEON-ядрами), затем iOS, WebAssembly и т.д.

Схема зависимостей:

```
0 Фундамент → 1 Ядро (IR + ii-ref) → 2 Быстрый ii-cpu (+Android) → 3 ONNX/CV ─┐
                                                           └→ 4 LLM ─────┼→ 5 Мульти-бэкэнд + CUDA + TensorRT
                                                                         │        ↓
                                                                         └──→ 6 Расширение → 7 Обучение
```

Этапы 3 и 4 технически независимы; ONNX идёт первым по приоритету (первая тестовая модель — YOLOv8).
CI/CD спланирован в [ci.md](ci.md).

## Этап 2 — Быстрый ii-cpu + Android

> **Статус: реализован.** Локально проверен на Windows (MSVC, MSVC shared, MSVC+ASan, clang-cl, MinGW GCC,
> MinGW Clang) и на телефоне Android (Snapdragon 732G, NEON) через `ctest --preset android-arm64-release`.
> AVX-512 проверяется в CI под Intel SDE (на машине разработки AVX-512 нет), Linux ARM64 и macOS — в CI.
> Сделано: SIMD-слой (generic/avx2/avx512/neon) и векторная математика с измеренной точностью; GEMM (BLIS,
> предупаковка константных весов, f16/bf16 веса, GEMV) на уровне OpenBLAS для больших матриц (на всех ядрах — быстрее),
> f32 GEMV — ~80% OpenBLAS, разрыв и план — в [bench/results/stage2-cpu.md](../bench/results/stage2-cpu.md);
> поэлементные операции через интерпретатор программ над тайлами + проход фьюзинга цепочек
> (`fused_elementwise`); редукции, softmax, layer/rms_norm, sdpa (GQA, causal, маски); reshape/permute/concat;
> CSE и шаблон `matmul + bias → linear`; совместное использование памяти (view для reshape, in-place для
> поэлементных); профайлер (`Session::set_profiling`, Chrome trace) и `ii run`; Android (пресеты NDK, запуск тестов
> через adb, эмулятор в CI). Перенесено: ISA-варианты `avx_vnni`/`neon_dotprod`/`neon_i8mm` и `rope` — в этап 4
> (нужны квантованным ядрам и LLM); шаблоны нормализаций/GELU/SiLU из примитивов и conv через GEMM — в этап 3
> (появляются вместе с импортом ONNX); активация в эпилоге GEMM (сейчас — отдельный фьюзнутый проход), автоподбор
> числа потоков для memory-bound GEMV на big.LITTLE и освобождение исходных весов после предупаковки — этап 4.

**Цель:** собственный CPU-бэкэнд, сопоставимый по скорости со зрелыми библиотеками, на любом CPU и ОС.

- SIMD-слой, runtime-диспетчер ISA (`generic`, `avx2`, `avx_vnni`, `avx512`, `neon`, `neon_dotprod`, `neon_i8mm`),
  `II_CPU_ISA`.
- GEMM f32 (BLIS-подход, предупаковка весов), f16/bf16 веса; GEMV.
- Поэлементные операции и редукции с фьюзингом цепочек; softmax, нормализации, rope.
- Распараллеливание с динамической раздачей (гибридные CPU: Intel P/E, Apple, big.LITTLE).
- Планировщик: `ii-cpu` предпочтительнее, `ii-ref` — фолбэк для того, что ещё не ускорено.
- Проходы: фьюзинг шаблонов (linear+act, нормализации), упаковка весов.
- Профайлер + Chrome trace.
- **Android**: пресет NDK (arm64-v8a, x86_64), CI-сборка, тесты на эмуляторе/устройстве.

**Готово, когда:** все тесты операций проходят для `ii-cpu` на всех ISA (AVX-512 — через SDE, NEON — на ARM64 Linux,
macOS и Android); цели микробенчмарков GEMM/поэлементных достигнуты или задокументирован разрыв и план; сравнение с
OpenBLAS — в `bench/results/`.

## Этап 3 — ONNX и «классические» модели (первый «настоящий» сценарий)

> **Статус: реализован.** Локально проверен на Windows (MSVC, MSVC shared, MSVC+ASan, clang-cl, MinGW GCC,
> MinGW Clang) и на телефоне Android; Linux ARM64, macOS и эмулятор — в CI. Сделано: собственный декодер protobuf и
> импорт ONNX (~130 операторов, opset 1–23+): символьное отслеживание вычислений над формами (Shape → Gather → Concat →
> Reshape и т.п.), поэтому модели с динамическими batch/sequence импортируются с символьными размерностями; функции
> модели, `If` с известным при загрузке условием, внешние данные (только внутри каталога модели),
> `LoadOptions::dims` / `constant_inputs`. Новые операции `resize`, `topk`. В ii-cpu: свёртки через GEMM с неявным
> im2col (панели упаковываются один раз на изображение) и предупаковкой весов, depthwise-свёртки, пулинги, resize;
> эпилог свёртки — внутренняя операция `fused_conv` (активации, SiLU, residual; batch_norm после импорта становится
> поканальными константами эпилога). `.npy` / `.npz` (свой inflate) в публичном API `ii/io.h`; CLI: `ii run` с
> `.npz`/`.npy`/изображениями, `--save-outputs`, `--top`, `ii bench`, `ii inspect` для ONNX; пример `examples/yolo`
> (letterbox, декодирование, NMS, отрисовка). Тесты: официальный набор операторных тестов ONNX — 1005 из 1884 случаев
> проходят на ii-ref и ii-cpu (CI `onnx-conformance` со списком ожидаемых), модели YOLOv8n, ResNet-50 (2 экспорта),
> MobileNetV2 (2 экспорта), BERT-base (2 экспорта) совпадают с ONNX Runtime (~1e-6; CI `models` и `nightly.yml`),
> фаззеры ONNX и npy/npz (+ 30 минут каждого в nightly). Задержка: ×1.1–1.25 к ONNX Runtime на BERT и YOLOv8n,
> ×1.5 на ResNet-50, ×1.9 на MobileNetV2 — разрыв и план в
> [bench/results/stage3-onnx.md](../bench/results/stage3-onnx.md) (раскладка NCHWc и прямые ядра свёрток).
> Перенесено: NCHWc / прямые ядра / Winograd — следующий шаг оптимизации CPU; `if`/`loop` с условием во время
> выполнения и `nms` как операция — вместе с выходами, размер которых зависит от данных (ONNX NonMaxSuppression,
> NonZero); распознавание attention-шаблонов в `sdpa` — этап 4 (вместе с attention для LLM); conv_transpose, 3-D
> окна и cubic resize в ii-cpu — по необходимости (сейчас ii-ref); `release.yml` (v0.1), `abi-interop`, `docs.yml`.

**Цель:** запуск произвольных ONNX-моделей (CV, энкодеры, аудио); первая цель — YOLOv8.

- Собственный декодер protobuf, импорт ONNX (opset 13–21+), external data, таблица маппинга операций; фаззинг.
- Свёртки (im2col+GEMM → прямые / Winograd / depthwise), пулинги, фолдинг batch_norm, раскладка NCHWc.
- Операции, нужные детекторам: resize/upsample, sigmoid/silu-цепочки, concat/split, `topk`, `nms` (как составная
  операция с эталоном).
- `if`/`loop` (подграфы), распознавание attention-шаблонов в `sdpa`.
- CLI: `ii run` с `.npy/.npz`/изображениями, `ii inspect`, `ii bench`.
- Пример `examples/yolo`: загрузка изображения, инференс, декодирование боксов + NMS, отрисовка результата.
- Тесты моделей в CI: манифест моделей (URL + sha256), кэш, сверка с ONNX Runtime.

**Готово, когда:** YOLOv8n/s, ResNet-50, MobileNetV2, BERT-base дают результаты в допуске относительно ONNX Runtime
(для YOLO — совпадение боксов/классов после NMS); задержка сопоставима с ORT CPU EP; ONNX-фаззер работает в CI.

> в текстовом IR, данные констант — указателями без копирования). Загрузка (`src/plugin/host.cpp`) из
> `ContextOptions::plugin_paths`, `II_PLUGIN_PATH` и каталога библиотеки; `ContextOptions::plugin_options`;
> состояния плагина «loaded / unavailable / failed» в `Context::plugins()` и `ii info`. SDK плагинов
> (`src/plugin/sdk.h`, `II_DEFINE_BACKEND_PLUGIN`) превращает обычные C++-бэкэнды в плагин. `ii-test-remote`
> собирается и плагином `ii-backend-test-remote`; весь набор тестов проходит с устройствами из плагина (в CI —
> отдельный шаг), в том числе крест-накрест: ядро MinGW GCC + плагин MSVC и ядро MSVC + плагин MinGW (1654 из
> 1654). `ii check-backends` (и `check_backends()` в API): 29 небольших моделей частых операций на каждом бэкэнде
> против ii-ref.
>
> **5.3.** Плагин `ii-backend-cuda` (`src/backends/cuda/`): собирается там, где CMake находит CUDA (на Windows —
> пресетами MSVC), а ядро, собранное MinGW, загружает плагин MSVC. CUDA runtime слинкован статически, cuBLASLt и
> NVRTC загружаются при старте (без них или без GPU плагин «unavailable» с причиной). Бэкэнд на каждый GPU: память
> `cudaMalloc`, очередь — CUDA stream сессии, ошибки, найденные на GPU (индекс `gather` вне диапазона), доходят до
> вызывающего как на CPU. Поэлементные операции и фьюженные цепочки генерируются из IR в CUDA C++ и компилируются
> NVRTC (общий модуль для одинаковых программ); matmul / linear / conv / `fused_conv` — cuBLASLt (дескрипторы на
> стеке, алгоритм кэшируется по форме; веса f16/bf16 при f32-активациях; TF32 по опции), свёртки 1×1 — один GEMM,
> остальные — im2col + GEMM, групповые — прямое ядро, эпилог `fused_conv` — сгенерированное ядро; ядра nvcc для
> редукций, argmax, softmax, layer/rms norm, перемещений, pad/tile/gather, iota/fill, пулинга, resize. Опции
> `cuda.devices / tf32 / library_path / prefer` (`ContextOptions::plugin_options` или новый `II_PLUGIN_OPTIONS`).
> Весь набор тестов (1662) проходит с `cuda.prefer=1` — каждая операция, для которой у ii-cuda есть ядро, идёт на
> GPU — в MSVC Release и Debug и в MinGW GCC с плагином MSVC; `cuda_test.cpp` проверяет каждую ветку ядер против
> ii-ref; `ii check-backends`: 29 из 29. ResNet-50, YOLOv8n, BERT работают на GPU и совпадают с ONNX Runtime;
> скорость на RTX 5080 — `bench/results/stage5-cuda.md` (ResNet-50 ×2: 3.3 мс против 21.7 на CPU, BERT 8×128: 17
> против 212). Попутно: планировщик больше не раскладывает «застрявшую» составную операцию, если на устройстве
> соседей нет ни одного бэкэнда; профилирование ждёт каждый шаг устройства (время шага — его собственное).
>
> **5.4.** LLM на `ii-cuda`. Произведения с весами всех блочных типов GGUF (`q4_0` … `q8_K`) и f16/bf16: при decode
> (до 8 строк) — собственный GEMV, который декодирует блоки в f32 (4 потока на 32 элемента — объединённые чтения;
> 1–4 варпа на строку, автотюнинг), при prefill — веса декодируются в f16 срезами и умножаются cuBLASLt на тензорных
> ядрах, 16-битные веса — без декодирования, x раскладывается на 16-битные части (точность ~f32). Активации не
> квантуются в 8 бит, поэтому GPU ближе к точному результату, чем CPU: против ii-ref (f32) KL ~3e-6, у CPU ~4e-3.
> `sdpa`: для промптов — FlashAttention-2 на тензорных ядрах (`mma.sync`, sm 8.0+, головы 64/96/128; f32-операнды
> раскладываются на две f16-части), в 6–9 раз быстрее ядра на CUDA-ядрах; для decode — online softmax и split-K
> с разбиением только по формам (записывается в граф). `rope`, `slice_update` на месте (KV-кэш на GPU), `dequantize`.
> CUDA Graphs: рантайм записывает подряд идущие шаги устройства, чьи ядра это допускают (`Kernel::can_record`), со
> второго запуска с теми же аргументами и дальше повторяет запись одной командой; функции записи добавлены в конец
> таблицы ABI плагинов (`struct_size`), `ii-test-remote` тоже записывает — логика проверяется без GPU; decode
> ускорился вдвое, ONNX-модели — до 1.6× (BERT 2×32: 2.55 мс против 3.97). Автотюнинг с кэшем
> (`cuda-<uuid>.json` в каталоге кэша ii; `cuda.autotune`, `cuda.cache`): калибровка устройства для планировщика
> (запуск ядра в графе, память, канал), алгоритм cuBLASLt для каждой формы произведения, варпы на строку GEMV.
> Планировщик: несколько стартовых планов (жадный и «всё на устройство»), представления бесплатны (`reshape`;
> `permute`, двигающий только оси размера 1, рантайм выполняет как представление) — LLM без подсказок целиком
> уходит на GPU; при лимите памяти начало модели уходит на CPU (Llama-3.2-1B с лимитом 500 МБ: тот же текст,
> 133 ток/с; GPU — 509, CPU — 85). Весь набор тестов (1671) проходит с GPU в приоритете, с планировщиком «как есть»
> и на симулированных устройствах (MSVC Release и Debug, MinGW GCC и Clang с плагином MSVC); HF-модели на GPU
> совпадают с transformers (логиты до 8e-6, жадная генерация, перплексия TinyLlama 9.1393). Против llama.cpp
> b12728 CUDA на RTX 5080 (KV f16): pp512 — 0.72–0.91 на квантованных моделях (Qwen2.5-0.5B: 57 600 против
> 63 400 ток/с), tg128 — 0.56–0.73 (569 против 874) — [bench/results/stage5-cuda.md](../bench/results/stage5-cuda.md).
> Разрыв задокументирован: decode упирается в число коротких ядер на слой (~17), prefill — в декодирование весов в
> f16 и f16-GEMM вместо int8-MMQ; перенесено: слияние linear с общим входом и остаточного сложения, MMQ, тензорный
> attention для голов 256 (gemma-3).
>
> **5.5.** Графовые бэкэнды и TensorRT. В ядре: `Backend::compiles_subgraphs()` и внутренняя операция `subgraph`
> (часть графа как IR-программа; константы модели — её входы; разложение — та же часть обратно). После планирования
> проход `runtime/partition.h` собирает для графового бэкэнда узлы его устройства, которые он поддерживает (какой бы
> бэкэнд этого устройства ни выбрал планировщик), в связные выпуклые части (часть с путём наружу и обратно режется на
> узле вне её) и отдаёт часть бэкэнду, если его оценка всей части лучше суммы оценок её узлов; узлы, которые
> планировщик сам отдал графовому бэкэнду, а тот не может скомпилировать, уходят следующему по скорости бэкэнду.
> Лимиты памяти и offload решаются раньше, так что графовому бэкэнду достаётся только то, что идёт на GPU. ABI
> плагинов дополнен в конец: `backend_flags` (графовый бэкэнд), `queue_native_handle` и `native_queue` в контексте
> запуска (`run_context_size` у хоста) — ядро плагина, которому достался поток другого плагина того же устройства,
> ставит работу в него (CUDA stream); память и очереди устройства берутся у первого бэкэнда ядер (ii-cuda), так что
> engine TensorRT и ядра ii-cuda идут в одном потоке без копий. Симулированное устройство получило графовый бэкэнд
> `ii-test-graph` (`graph=1`): разбиение и смешанные планы проверяются без GPU. Плагин `ii-backend-tensorrt`
> (`src/backends/tensorrt/`, nvinfer загружается при старте): трансляция IR прямо в строго типизированную
> `INetworkDefinition` (f32 остаётся f32; TF32 — по `tensorrt.tf32`) — поэлементные, редукции, произведения, свёртки
> (в т.ч. с весами из модели), пулинг, resize, нормализация, softmax, перемещения, gather/scatter и фьюженные
> операции ii; rms_norm, log_softmax и attention без KV-кэша — через разложение ii; операции LLM (rope, запись в
> KV-кэш, attention с `kv_len`, квантованные веса) остаются за ii-cuda. Символьные размерности — динамические
> размерности сети, формы от символов вычисляются в сети; профиль на символ — 1 .. 2× первого значения (`opt` — оно
> само), значение вне профиля строит ещё engine (`tensorrt.profile` задаёт диапазоны). Кэш engine на диске
> (`<кэш ii>/tensorrt/`, ключ: программа и веса, профиль, опции, версия TensorRT, GPU, ревизия трансляции) и timing
> cache TensorRT; engine работает в памяти арены сессии (`setDeviceMemoryV2`) и записывается в CUDA graph, как и
> ядра ii-cuda (одиночный шаг TensorRT тоже). Оценка части: 0.7 × roofline + запуск на каждую операцию, не
> сливающуюся с соседями, + 5 мкс на постановку engine — CNN и энкодеры трансформеров становятся одним engine, мелкие
> куски между ядрами LLM остаются за ii-cuda (скорость LLM с плагином TensorRT и без него одинакова). Весь набор тестов
> (1686) проходит в семи режимах: без плагинов, ii-cuda в приоритете, TensorRT в приоритете (остальное на CPU),
> TensorRT и ii-cuda в приоритете, планировщик «как есть», симулированные устройства, симулированный графовый бэкэнд
> (MSVC Release; Debug — графовый бэкэнд и TensorRT; MinGW GCC и Clang — без плагинов и с плагинами MSVC);
> `tensorrt_test.cpp`: каждая транслируемая операция против ii-ref, общий GPU с ii-cuda, кэш engine, профили, записанные
> прогоны, параллельные сессии, случайные модели. Против ONNX Runtime: относительная ошибка 1–3e-6. Против `trtexec`
> (TensorRT 10.16.1, CUDA graphs): engine работает со скоростью `trtexec`, разница — копирование входов и выходов из
> pageable-памяти (ResNet-50 ×2: 1.61 мс против 1.40, было 2.97 на ii-cuda; ×16: 6.45 против 5.78; BERT 2×32: 1.93
> против 1.38; MobileNetV2: 0.52 против 0.38) — [bench/results/stage5-cuda.md](../bench/results/stage5-cuda.md).
> Попутно найдена ошибка TensorRT 10.16 (softmax + сумма всех элементов малого тензора при слиянии считаются неверно;
> воспроизводится `trtexec` на ONNX из двух узлов) — транслятор её обходит. Дальше: pinned-буферы для копий,
> fp16/int8-режимы TensorRT, сборка плагина на Linux.

**Цель:** библиотека сама выбирает между CPU, собственными CUDA-ядрами и TensorRT и делит модель между устройствами.

- Полноценный планировщик: стоимостная модель, разбиение графа, домены памяти, пересылки, события, ограничения
  памяти, автоматический offload слоёв, автотюнинг с кэшем, `ii inspect --plan` с объяснениями.
- Тестовый бэкэнд `ii-test-remote` (межустройственные сценарии без GPU).
- Плагинный ABI `ii_backend_plugin_v1`, загрузка плагинов; плагин без рантайма SDK сообщает «недоступен». ✅ (5.2)
- **`ii-cuda`**: свои ядра (квантованный matmul, attention, фьюженные поэлементные через NVRTC), cuBLASLt,
  CUDA Graphs для decode; LLM на GPU с offload части слоёв на CPU.
- **Плагин TensorRT**: трансляция партиций IR в `INetworkDefinition`, профили динамических форм, кэш движков на
  диске, общий домен памяти с `ii-cuda` (смешанные планы TRT + свои ядра без копий через host).
- Self-hosted GPU-раннер в CI (машина с RTX 5080).
- `ii check-backends`. ✅ (5.2)

**Готово, когда:** дифференциальные тесты проходят для `ii-cuda` и TensorRT; модель, не помещающаяся в VRAM,
автоматически делится между GPU и CPU; на наборе моделей (ResNet-50, BERT, LLM) планировщик выбирает план не хуже
лучшего ручного; производительность сравнена с `trtexec` и llama.cpp CUDA.

C ABI плагина решает обе проблемы.

## Этап 6 — Расширение

По приоритетам, определяемым бенчмарками и запросами:

- серверный режим (`ii serve`, OpenAI-совместимый API);
- привязки: Python (nanobind), C#, Rust — поверх C ABI;
- минимальная сборка под конкретные модели (`II_MINIMAL`).

## Этап 7 — Обучение

**Цель:** обучение и дообучение моделей средствами ii на любом бэкэнде.

- Правила градиентов для всех операций, проход autodiff, фьюженные backward-операции (в т.ч. для `ii-cuda`).
- `nn::Module`, трассировка в граф, функции потерь, оптимизаторы (SGD, Adam, AdamW) как фьюженные операции.
- Шаг обучения как один `Program`, DataLoader, чекпоинты (safetensors).
- Mixed precision, gradient checkpointing, LoRA/QLoRA для LLM.
- CLI: `ii train`.

**Готово, когда:** проверка градиентов конечными разностями для всех операций; MNIST-MLP и маленький CNN достигают
эталонной точности; кривая обучения совпадает с PyTorch при одинаковой инициализации; LoRA-дообучение маленькой LLM
снижает loss на целевом наборе (на CPU и на CUDA).
