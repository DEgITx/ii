# ii — архитектура

> Статус: проект (design draft). Документ описывает целевую архитектуру; порядок реализации — в [roadmap.md](roadmap.md),
> стратегия тестирования и измерений — в [testing-and-benchmarks.md](testing-and-benchmarks.md).

## 1. Цели, не-цели, принципы

### Цели

1. **Инференс нейросетей** (в первую очередь) и **обучение** — одной библиотекой, на одном внутреннем представлении.
2. **Работает везде**: от слабого x86/ARM без GPU и без AVX до многоядерных серверов и дискретных GPU. Один бинарник
   для x86-64 запускается на любом x86-64 CPU (диспетчеризация ISA во время выполнения).
3. **Сама выбирает бэкэнд**: собственные бэкэнды `ii-*` и сторонние (ONNX Runtime, OpenVINO, TensorRT, CoreML, oneDNN …),
   с учётом возможностей устройства, стоимости операций, объёма памяти и стоимости пересылок.
4. **Собственный бэкэнд ii**, который работает везде, корректен (есть эталон) и быстр (цели — в % от roofline железа).
5. **Легко встраивается**: ноль обязательных зависимостей, нет глобального состояния, внедряемые аллокатор/потоки/логгер,
   стабильный C ABI, статическая и динамическая сборка, `find_package(ii)` / `add_subdirectory`.
6. **Хорошо спроектирована и документирована**: явные слои, явные инварианты, каждое решение записано.
7. **CLI `ii`** для запуска, инспекции, бенчмарков, конвертации и квантизации моделей.

### Не-цели (по крайней мере на старте)

- Замена PyTorch как исследовательского фреймворка с динамическим Python-кодом.
- Распределённое обучение на кластере (многоузловое). Многоустройственное на одной машине — позже.
- Поддержка big-endian платформ (заявляем только little-endian).

### Принципы (по ним решаются спорные вопросы)

| # | Принцип | Следствие |
|---|---------|-----------|
| P1 | **Корректность прежде скорости** | У каждого быстрого пути есть эталонная реализация и дифференциальный тест против неё. |
| P2 | **Один IR для всего** | Импорт, оптимизации, инференс, обратный проход и шаг оптимизатора — всё графы одного IR. Любая оптимизация и любой бэкэнд автоматически работают и для обучения. |
| P3 | **Бэкэнд обязан уметь только примитивы** | Составные операции (softmax, layer_norm, attention…) раскладываются в примитивы, если бэкэнд не реализует их сам. Новый бэкэнд дёшев. |
| P4 | **Всегда работает** | `ii-ref` реализует все операции на любом CPU; планировщик всегда может откатиться на него. |
| P5 | **Ноль обязательных зависимостей ядра** | Всё стороннее — опционально и, как правило, в виде плагинов (отдельных .so/.dll). |
| P6 | **Нет глобального состояния** | Всё живёт в `ii::Context`; аллокатор, пул потоков, логгер — внедряемы. Никакой регистрации через статические инициализаторы. |
| P7 | **Ноль аллокаций в установившемся `run()`** | Вся память планируется при компиляции; проверяется тестом со счётчиком аллокаций. |
| P8 | **Измеримость** | Каждый горячий путь имеет бенчмарк; цели производительности выражены в % от пика FLOPS / пропускной способности памяти. |
| P9 | **Объяснимость** | Всегда можно узнать, почему выбран бэкэнд, как разбит граф и куда ушло время (`ii inspect --plan`, профайлер). |

## 2. Слои

```
┌──────────────────────────────────────────────────────────────────────────────┐
│  tools/ii (CLI)                       bindings: C, Python*, C#*, Rust* (*позже) │
├──────────────────────────────────────────────────────────────────────────────┤
│  Public API         C++: include/ii/*.hpp          C ABI: include/ii/ii.h       │
├──────────────────────────────────────────────────────────────────────────────┤
│  Domain             ii::llm   — архитектуры, токенизаторы, KV-cache, сэмплинг     │
│                     ii::nn / ii::train — модули, autodiff, оптимизаторы, циклы   │
├──────────────────────────────────────────────────────────────────────────────┤
│  Runtime            Context · Model · Program · Session                         │
│                     Planner (выбор бэкэндов) · MemoryPlanner · Executor · Profiler│
├──────────────────────────────────────────────────────────────────────────────┤
│  Compiler           IR · OpSet · ShapeInference · Passes · Autodiff · Patterns  │
├──────────────────────────────────────────────────────────────────────────────┤
│  Formats            GGUF · safetensors(+HF config) · ONNX · .ii (нативный)      │
├──────────────────────────────────────────────────────────────────────────────┤
│  Backend API ──┬── собственные: ii-ref · ii-cpu · ii-vulkan · ii-cuda · ii-metal │
│                └── плагины:     onnxruntime · openvino · tensorrt · coreml · …    │
├──────────────────────────────────────────────────────────────────────────────┤
│  Core               Status/Result · Log · Allocator · ThreadPool · CpuInfo ·     │
│                     MappedFile · f16/bf16 · SmallVector · Json · Hash            │
└──────────────────────────────────────────────────────────────────────────────┘
```

**Правила зависимостей** (проверяются CMake-таргетами — каждый слой отдельная библиотека-объект):

- Зависимости только вниз. `core` не знает ни о чём.
- `formats` зависит от `ir`, но не от `runtime` (загрузчик просто строит граф и ссылки на веса).
- Бэкэнд зависит от `backend-api`, `ir` (только чтение) и `core`. Никогда — от `runtime`-внутренностей или другого бэкэнда.
- `llm` и `train` используют только публичные/полупубличные интерфейсы `runtime` и `ir` — это гарантирует, что
  API достаточно выразителен для сторонних пользователей.

## 3. Объектная модель публичного API

```
Context      устройства, бэкэнды, пул потоков, аллокаторы, логгер, кэш тюнинга   (1 на приложение)
  └─ Model   граф + веса (mmap), неизменяемая                                    (разделяемая)
      └─ Program   скомпилированный план под конкретные устройства, неизменяемый (разделяемый)
           └─ Session   состояние исполнения: арена активаций, KV-cache,         (1 на поток/запрос)
                        привязки входов/выходов
```

| Объект | Потокобезопасность | Стоимость создания |
|--------|--------------------|--------------------|
| `Context` | потокобезопасен | дорого (обнаружение устройств) |
| `Model` | неизменяем → безопасен | дёшево (mmap, ленивое чтение) |
| `Program` | неизменяем → безопасен | дорого (проходы, планирование, упаковка весов) — кэшируется |
| `Session` | **не** потокобезопасна, одна на поток | дёшево (выделение арены) |

Это даёт главное для встраивания и серверов: веса и скомпилированный план разделяются, а параллельные запросы
работают каждый в своей `Session`.

### Пример: общий инференс (C++)

```cpp
#include <ii/ii.hpp>

int main() {
    auto ctx     = ii::Context::create().value();                 // обнаружение устройств и бэкэндов
    auto model   = ii::Model::load(ctx, "resnet50.onnx").value();
    auto program = model.compile({.policy = ii::Policy::Latency}).value();
    auto session = program.new_session().value();

    ii::Tensor image = ii::Tensor::wrap(pixels, ii::f32, {1, 3, 224, 224});  // zero-copy
    auto out = session.run({{"input", image}}).value();
    std::span<const float> logits = out[0].data<float>();
}
```

### Пример: LLM

```cpp
auto llm  = ii::llm::Llm::load(ctx, "qwen2.5-1.5b-instruct-q4_k_m.gguf").value();
auto chat = llm.new_chat({.temperature = 0.7f, .top_p = 0.9f});
chat.send("Привет! Кто ты?", [](std::string_view piece) { std::cout << piece << std::flush; });
```

### Пример: обучение

```cpp
namespace nn = ii::nn;

struct Mlp : nn::Module {
    nn::Linear fc1{this, 784, 256}, fc2{this, 256, 10};
    ii::Var forward(ii::Var x) { return fc2(ii::relu(fc1(x))); }
};

Mlp net;
auto step = ii::train::compile_step(ctx, net, ii::loss::cross_entropy, ii::optim::AdamW{.lr = 1e-3f}).value();
for (auto& [x, y] : loader) step.run(x, y);   // forward+backward+AdamW — один скомпилированный Program
```

### Пример: C ABI

```c
ii_context* ctx;  ii_model* model;  ii_program* prog;  ii_session* s;
II_TRY(ii_context_create(NULL, &ctx));
II_TRY(ii_model_load(ctx, "model.onnx", &model));
II_TRY(ii_program_compile(model, NULL, &prog));
II_TRY(ii_session_create(prog, &s));
II_TRY(ii_session_bind_input(s, "input", &tensor_desc));
II_TRY(ii_session_run(s));
```

### Обработка ошибок

- Библиотека **не бросает исключений** через свои границы (многие встраивающие приложения собираются с
  `-fno-exceptions`): `ii::Status` (код + сообщение) и `ii::Result<T>` (аналог `std::expected`, свой — чтобы не
  требовать C++23). Макрос `II_TRY(expr)` для проброса.
- `II_ASSERT` — проверки инвариантов в отладочной сборке; `II_CHECK` — всегда, для «невозможных» состояний.
- В C ABI — коды `ii_status` + `ii_last_error_message()` (thread-local).

## 4. Тензоры и типы данных

### DType

| Класс | Типы |
|-------|------|
| float | `f32`, `f16`, `bf16`, `f64` (только ref/тесты), `f8e4m3`, `f8e5m2` (позже) |
| int | `i8`, `u8`, `i16`, `i32`, `i64`, `bool` |
| блочно-квантованные | `q8_0`, `q4_0`, `q4_1`, `q5_0`, `q5_1`, `q4_k`, `q5_k`, `q6_k`, `q8_k`, … — побайтово совместимы с раскладками GGUF, чтобы веса грузились zero-copy через mmap |
| поканальные квант. | `i8`/`u8`/`i4` + отдельные тензоры scale/zero_point (ONNX QDQ, GPTQ/AWQ) |

Блочные типы описываются `DTypeTraits { block_size, bytes_per_block, … }`; квантованным может быть только последнее
измерение, шаги измеряются в блоках.

### Shape, Tensor, Buffer, Device

- `Shape` — `SmallVector<int64_t, 8>` (без кучи), ранг ≤ 8. В IR размер может быть символом (см. §5).
- `Buffer` — участок памяти на `Device` со счётчиком ссылок. Источники: собственная аллокация, mmap файла,
  внешняя память пользователя (zero-copy `Tensor::wrap`), память бэкэнда (GPU).
- `Tensor` = `{Buffer, offset, dtype, shape, strides}`. `reshape`/`permute`/`slice`/`expand` — представления без копий.
- Выравнивание по умолчанию — 64 байта (кэш-линия / AVX-512).
- Публичный `Tensor` всегда логически row-major; физические раскладки (NCHWc, упакованные панели GEMM) — внутреннее дело
  бэкэнда и наружу не видны.

## 5. IR (промежуточное представление)

- **`Graph`** — SSA-граф в топологическом порядке: `Node`ы (операции) производят `Value`ы.
- **`Value`** — `{id, TensorType{dtype, SymShape}, producer, users}`. Разновидности: вход, выход, константа (ссылается на
  `Buffer`, в т.ч. mmap), промежуточное, **состояние** (state).
- **State-значения** читаются в начале `run()` и записываются в конце; живут в `Session` между запусками. Один механизм
  покрывает KV-cache трансформеров, скрытые состояния RNN, а при обучении — параметры и моменты оптимизатора.
- **Символьные размеры**: `Dim` — константа или выражение над символами (`N`, `seq`, `past`): аффинные выражения и
  произведения — этого хватает для reshape голов внимания. Символы могут иметь верхние границы (`seq ≤ 4096`).
- **Атрибуты** — типизированный `variant` (int, float, string, списки, тензор, подграф).
- **Подграфы** — для `if`/`loop` (нужны части ONNX-моделей). Цикл генерации LLM живёт в runtime, не в графе.
- **`Graph::verify()`** — проверка SSA, типов, форм, топологии. Вызывается после каждого прохода в debug-сборке.
- **Текстовый формат** для отладки и тестов проходов:

  ```
  %3 : f32[N, 4096] = matmul(%x, %w1) {trans_b = true}
  %4 : f32[N, 4096] = silu(%3)
  ```
  Тесты проходов пишутся как «вход → ожидаемый текст» (в стиле FileCheck) + численная эквивалентность.

## 6. Набор операций (OpSet)

### Примитивы и составные

**Примитивы** (каждый бэкэнд реализует их или отказывается от узла):

| Группа | Операции |
|--------|----------|
| унарные | neg, abs, exp, log, sqrt, rsqrt, recip, sin, cos, tanh, sigmoid, erf, relu, floor, ceil, round, sign, not |
| бинарные (broadcast) | add, sub, mul, div, pow, max, min, mod, eq, ne, lt, le, gt, ge, and, or, xor |
| прочие поэлементные | where, cast, clamp |
| редукции | sum, mean, max, min, prod, argmax, argmin |
| линейная алгебра | matmul (батч, broadcast, транспонирование, квантованный B) |
| свёртки | conv (N-d, groups, dilation, pad), conv_transpose, max_pool, avg_pool |
| перемещение данных | reshape, permute, slice, expand, concat, split, pad, gather, scatter, tile, flip, cumsum |
| создание | iota, fill, random_uniform/normal (для dropout/инициализации) |
| квантование | quantize, dequantize |
| управление | if, loop |

**Составные** (имеют правило разложения на примитивы; бэкэнд может реализовать их нативно — так и делается для
скорости): gelu, silu, softmax, log_softmax, layer_norm, rms_norm, group_norm, batch_norm, linear (matmul+bias),
rope, sdpa (scaled dot-product attention: маска, causal, GQA, KV-cache), swiglu, cross_entropy, adamw_step, …

### OpSchema — единственный источник правды об операции

```cpp
struct OpSchema {
    std::string_view name;
    int since_version;
    Arity inputs, outputs;
    TypeConstraints types;
    ShapeFn  infer_shape;          // символьный вывод форм
    DecomposeFn decompose;         // nullptr для примитивов
    GradFn   gradient;             // правило обратного прохода, выраженное через ii-операции
    CostFn   cost;                 // flops и байты — для планировщика и roofline-отчётов
    std::string_view doc;          // из этого же генерируется справочник операций
};
```

**Добавление операции** = schema + эталонное ядро в `ii-ref` + тест соответствия + (если дифференцируема) правило
градиента и проверка конечными разностями. Чек-лист — в `docs/guides/adding-an-op.md`.

## 7. Компилятор: конвейер проходов

```
импорт → канонизация → вывод форм → свёртка констант → DCE/CSE → алгебраические упрощения
      → распознавание шаблонов/фьюзинг → [autodiff, если обучение] → разбиение по бэкэндам
      → понижение под бэкэнд (раскладки, упаковка весов, разложение неподдерживаемых составных)
      → планирование памяти → ExecutionPlan
```

- **PassManager** с явными зависимостями проходов; `verify()` после каждого прохода в debug.
- **Свёртка констант** исполняет подграфы через `ii-ref` — без отдельного «вычислителя».
- **Сопоставление шаблонов** — небольшой декларативный DSL: `matmul → add(bias) → gelu` ⇒ `linear{act=gelu}`;
  распознавание «развёрнутого» attention из ONNX ⇒ `sdpa`; `x * rsqrt(mean(x²)+eps) * w` ⇒ `rms_norm`.
- **Инвариант проходов**: проход не меняет результат сверх допуска — проверяется автоматически в тестах (исполняем
  граф до и после прохода на случайных входах).

## 8. Бэкэнды

### Два вида бэкэндов под одним интерфейсом

1. **Kernel-бэкэнды** (`ii-ref`, `ii-cpu`, `ii-vulkan`, `ii-cuda`, `ii-metal`, плюс обёртки oneDNN/XNNPACK/cuBLAS):
   предоставляют ядра по операциям; расписание и память ведёт runtime ii. Реализуются через вспомогательный базовый
   класс `KernelBackend` с таблицей ядер `(op, dtype-ограничения, ISA) → kernel`.
2. **Graph-бэкэнды** (ONNX Runtime, OpenVINO, TensorRT, CoreML): забирают целые подграфы и компилируют их своим
   движком (аналог ORT `GetCapability` / TFLite delegates).

```cpp
namespace ii::backend {

struct DeviceInfo {
    DeviceKind  kind;                 // cpu, gpu, npu, …
    MemoryKind  memory;               // host, unified, discrete
    std::string name;
    uint64_t    memory_bytes;
    PerfModel   perf;                 // пиковые FLOPS по dtype, пропускная способность памяти и шины (оценка/замер)
};

enum class Support { No, Native, Fused };

class Backend {
public:
    virtual ~Backend() = default;
    virtual std::string_view name() const noexcept = 0;
    virtual std::span<Device* const> devices() noexcept = 0;

    /// Может ли бэкэнд исполнить узел на устройстве (dtype, атрибуты, формы).
    virtual Support supports(const ir::Node&, const Device&) const = 0;
    /// Graph-бэкэнды: какие максимальные подграфы они готовы забрать целиком.
    virtual std::vector<ir::NodeSet> claim(const ir::Graph&, const Device&) const { return {}; }
    /// Оценка времени (по умолчанию — roofline из OpSchema::cost и PerfModel устройства).
    virtual Cost estimate(const ir::Node&, const Device&) const;
    /// Компиляция партиции в исполняемый объект.
    virtual Result<std::unique_ptr<Executable>> compile(const ir::Partition&, Device&, const CompileOptions&) = 0;
};

class Executable {
public:
    virtual ~Executable() = default;
    virtual MemoryRequirements memory() const = 0;   // scratch/workspace — учитывается планировщиком памяти
    virtual Status execute(ExecContext&) = 0;         // без аллокаций
};

} // namespace ii::backend
```

### Устройства, память, синхронизация

- `Device` выделяет `Buffer`ы, копирует (host↔device, device↔device), даёт `Stream`ы и `Event`ы.
- На host-устройствах (CPU, unified-memory iGPU/Apple) копии между бэкэндами не нужны — планировщик это учитывает.
- Межустройственные переходы — явные узлы `transfer` в плане, с событиями синхронизации.

### Плагины

- Сторонние бэкэнды собираются как отдельные `ii-backend-<name>.dll/.so`, чтобы ядро не зависело от их SDK.
- Стабильная граница — C-структура `ii_backend_plugin_v1` (таблица указателей на функции) + экспортируемая
  `ii_backend_plugin_entry()`; рукопожатие по версии ABI. Внутри плагина — C++-обёртка, реализующая `Backend`.
- Плагины ищутся в каталоге рядом с библиотекой, в `II_PLUGIN_PATH` и в явно указанных путях `Context::Options`.
- Встроенные бэкэнды регистрируются **явно** в `Context::create()` (никаких статических инициализаторов —
  они ломаются при статической линковке и создают проблемы порядка инициализации).

### Планируемые бэкэнды

| Бэкэнд | Тип | Устройства | Приоритет |
|--------|-----|-----------|-----------|
| `ii-ref` | собственный, kernel | любой CPU | этап 1 — эталон и последний фолбэк |
| `ii-cpu` | собственный, kernel | x86-64 (SSE2…AVX-512/AMX), ARM64 (NEON…SVE), generic C++ | этап 2 |
| `ii-vulkan` | собственный, kernel | любые GPU с Vulkan 1.2+ (NVIDIA/AMD/Intel/мобильные) | этап 5 |
| `ii-cuda` | собственный, kernel (+cuBLAS/cuBLASLt) | NVIDIA | этап 5/7 |
| `ii-metal` | собственный, kernel | Apple | этап 7 |
| onnxruntime | плагин, graph | всё, что умеют его EP | этап 5 — «закрывает» длинный хвост ONNX-операций |

## 9. Автоматический выбор бэкэнда (Planner)

Цель: минимизировать оценочное время (или энергию — по политике) при ограничениях на память и возможности.

**Алгоритм:**

1. **Обнаружение.** `Context` опрашивает бэкэнды: устройства, `DeviceInfo`, поддерживаемые dtype. `PerfModel` берётся
   из таблицы известных устройств или замеряется микробенчмарком при первом запуске и кэшируется.
2. **Кандидаты.** Для каждого узла: `{(backend, device) | supports ≠ No}`; `ii-ref@cpu` присутствует всегда.
   Graph-бэкэнды заявляют подграфы через `claim()` — те становятся «суперузлами» с собственной оценкой.
3. **Стоимость.** `t(узел, backend, device)` — из `estimate()` (по умолчанию roofline: `max(flops/peak, bytes/bw)` +
   накладные на запуск); пересылка по ребру между разными памятями — `bytes / link_bw + latency`.
4. **Начальное назначение** — жадно в топологическом порядке (HEFT-подобно): минимизируем время узла + пересылки от
   уже назначенных предшественников.
5. **Улучшение** — локальный поиск: слияние «островков» (одиночный узел на другом устройстве между большими
   партициями) там, где это снижает суммарное время; устраняет пинг-понг пересылок.
6. **Ограничение по памяти.** Сумма весов + пик активаций на устройстве ≤ `capacity × (1 − reserve)`. При
   переполнении повторяющиеся блоки (слои трансформера) по одному переносятся на следующее по стоимости устройство —
   **автоматический offload слоёв**, когда модель не помещается в VRAM целиком.
7. **Автотюнинг (опционально).** `TuneMode::Measure`: прогнать top-K планов на реальных данных и выбрать лучший.
   Результат кэшируется по ключу `(хэш модели, формы, устройство, версия драйвера, версия ii)` в
   `<cache>/ii/tuning.json`. Так же тюнингуются параметры ядер (размеры блоков, число потоков для decode).

**Политики и переопределения:** `Policy::{Latency, Throughput, LowPower, LowMemory}`, список разрешённых/запрещённых
бэкэндов и устройств, лимиты памяти; переопределение через `CompileOptions`, CLI (`--backend cuda,cpu`) и
`II_BACKENDS`.

**Объяснение:** `ii inspect model --plan` печатает партиции, устройства, оценки и причины отказа бэкэндов
(«ii-vulkan: op `scatter` с dtype i64 не поддерживается»).

## 10. Runtime: память и исполнение

- **Планирование памяти**: интервалы жизни значений → смещения в арене алгоритмом «greedy by size» (как в TFLite);
  in-place для поэлементных операций над умирающими входами; отдельная арена на каждое устройство; workspace ядер
  учитывается как обычные значения. Константы (веса) живут вне арены (mmap или упакованные копии).
- **ExecutionPlan** — линейный массив шагов с заранее связанными аргументами (указатели, формы, страйды); выполнение —
  проход по массиву без виртуальной диспетчеризации по операциям и без аллокаций.
- **Динамические формы**: в плане хранится маленькая «программа форм» (байткод), вычисляющая конкретные размеры по
  значениям символов. Если у символов есть верхние границы — арена планируется на максимум один раз; иначе при
  превышении план памяти пересчитывается (редко, амортизированно), с кэшем по «корзинам» форм.
- **I/O binding**: пользователь может передать свои буферы входов и выходов (zero-copy), в т.ч. на GPU.
- **Профайлер**: время по шагам/партициям/пересылкам, экспорт в Chrome trace JSON (открывается в Perfetto):
  `ii run model --profile trace.json`.

## 11. Бэкэнд `ii-cpu`

### Диспетчеризация ISA во время выполнения

- Ядра в `src/backends/cpu/kernels/<isa>/` компилируются **несколько раз** с разными флагами:
  `generic` (SSE2 / NEON / чистый C++), `avx2` (AVX2+FMA+F16C), `avx_vnni`, `avx512` (F/BW/VL/DQ), `avx512_vnni_bf16`,
  `amx`, `neon_dotprod`, `neon_i8mm`, `sve`; позже `rvv` и `wasm_simd128`.
- `CpuInfo` (cpuid / `getauxval` / sysctl) выбирает лучший уровень; таблица ядер заполняется указателями на функции.
  Принудительный уровень: `II_CPU_ISA=generic|avx2|…` — так на одной машине тестируются все пути.
- **Ловушка ODR**: inline-функции/шаблоны, инстанцированные в TU с `-mavx2`, линкер может подставить и в generic-путь →
  SIGILL на старом CPU. Решение: весь ISA-специфичный код (включая шаблоны) — в отдельном пространстве имён
  `ii::cpu::II_ISA_NS`, общие заголовки в эти TU попадают только через него.

### SIMD-слой

Тонкая собственная абстракция `Vec<T, Isa>` (load/store/fma/reduce/convert) поверх интринсиков — для поэлементных
операций и редукций. Горячие микроядра (GEMM, квантованные dot-product) пишутся на интринсиках напрямую.

### GEMM (сердце производительности)

- BLIS-подход: упаковка A и B в панели, микроядро `MR×NR` в регистрах (напр. AVX2 f32 6×16, AVX-512 14×32,
  NEON 8×12), блокирование `MC/KC/NC` по размерам кэшей из `CpuInfo`.
- **Предупаковка весов при компиляции** (B — константа): упаковка не повторяется на каждом запуске.
- f16/bf16 веса — расширение в f32 при упаковке или на лету (F16C), аккумуляция в f32.
- Распараллеливание по блокам M/N с учётом общего L3.

### Квантованные ядра (ключ к слабому железу)

- **Decode LLM (GEMV, batch 1)** упирается в память: деквантизация на лету внутри dot-product, цель — ≥ 85–90%
  пропускной способности памяти.
- **Prefill / batch** — вычислительно ограничен: активации квантуются в int8 по блокам, затем int8×int4/int8
  dot-product (`vpdpbusd` AVX-VNNI/AVX512-VNNI, `sdot`/`smmla` на ARM).

### Attention, нормализации, поэлементное

- `sdpa`: тайловый flash-attention для CPU (онлайн-softmax, без материализации матрицы внимания), GQA, KV-cache.
- `rms_norm`, `layer_norm`, `rope`, `softmax`, `swiglu` — нативные фьюженные ядра.
- Цепочки поэлементных операций сливаются в один проход по памяти (фьюзинг loop-уровня).
- Аппроксимации (`exp`, `tanh`, `erf`) — явные, с задокументированной максимальной ошибкой и тестами; `-ffast-math`
  глобально **не** используется (ломает NaN/Inf).

### Потоки

- Собственный `ThreadPool`: `parallel_for(range, grain, fn)`; вызывающий поток участвует; короткое активное ожидание,
  затем сон на futex/condvar; цель — накладные расходы на запуск < 5 мкс.
- **Гибридные CPU** (P/E-ядра, как Core Ultra): статическое равное разбиение даёт простой быстрых ядер, поэтому работа
  раздаётся динамически кусками через атомарный счётчик. Опция привязки к P-ядрам для задач, чувствительных к задержке.
- Для decode, ограниченного памятью, оптимальное число потоков часто меньше числа ядер — подбирается автотюнингом.
- Внешний пул: встраивающее приложение может передать свою реализацию интерфейса `ii::Executor` (job system движка).
- **Детерминированный режим**: фиксированный порядок редукций (статическое разбиение) → побитовая повторяемость при
  одинаковом числе потоков.

## 12. GPU-бэкэнды ii

- **ii-vulkan** — универсальный GPU-бэкэнд (Windows/Linux/Android, все производители). Шейдеры GLSL → SPIR-V на этапе
  сборки; тяжёлые операции (matmul с cooperative matrix, attention, квантованный matmul) пишутся вручную; цепочки
  поэлементных операций — генерируются и компилируются во время выполнения (кэш пайплайнов на диске).
- **ii-cuda** — максимум производительности на NVIDIA: свои ядра + cuBLASLt для GEMM, NVRTC для сгенерированных
  фьюженных ядер, CUDA Graphs для снижения накладных на запуск в decode.
- **ii-metal** — Apple, unified memory (без копий host↔device).

Общая часть GPU-бэкэндов: генератор фьюженных поэлементных ядер из подграфа IR (один «кодоген», несколько диалектов:
GLSL / CUDA C / MSL).

## 13. LLM-подсистема (`ii::llm`)

Построена **поверх** общего IR и runtime, а не как отдельный движок — значит, автоматически получает все бэкэнды,
планировщик, offload и профайлер.

- **Архитектуры как код**: `src/llm/arch/llama.cpp`, `qwen.cpp`, `gemma.cpp`, `phi.cpp`, … строят граф через builder
  API по гиперпараметрам из GGUF-метаданных или HF `config.json`. MoE (Mixtral, Qwen-MoE) — позже.
- **KV-cache** — state-значения сессии; позже paged KV-cache для continuous batching.
- **Prefill и decode** — один граф с символом `seq`; планировщик может выбрать разные ядра/потоки для `seq = 1`.
- **Токенизаторы**: byte-level BPE (GPT-2/Llama 3/Qwen), SentencePiece (BPE/Unigram); из GGUF или `tokenizer.json`.
- **Шаблоны чата**: интерпретатор подмножества Jinja2, достаточного для реальных шаблонов из GGUF.
- **Сэмплинг**: цепочка greedy / temperature / top-k / top-p / min-p / repetition-penalty; позже грамматики (JSON),
  speculative decoding.
- **Стриминг** токенов через колбэк; отмена генерации.

## 14. Обучение (`ii::nn`, `ii::train`)

- **Autodiff как проход компилятора**: `ir::differentiate(graph, loss, params)` достраивает обратный граф по
  `OpSchema::gradient`. Градиенты — тоже ii-операции ⇒ работают на любом бэкэнде, проходят те же оптимизации.
  Для узких мест — фьюженные backward-операции (`softmax_ce_grad`, `conv_backward_*`, `sdpa_backward`).
- **Шаг обучения = один Program**: forward + backward + шаг оптимизатора (`adamw_step` — фьюженное ядро); параметры
  и моменты — state-значения сессии ⇒ ноль аллокаций на шаге.
- **Фронтенд**: `nn::Module` (Linear, Conv2d, Embedding, LayerNorm, RMSNorm, Attention, …), `ii::Var` — символьная
  переменная builder API, «трассировка» функции пользователя в граф (как `torch.compile`/JAX `jit`).
- **Возможности по мере развития**: mixed precision (bf16 вычисления + f32 master-веса, loss scaling для f16),
  gradient checkpointing (проход, вставляющий перевычисление), **LoRA/QLoRA** — дообучение адаптеров поверх
  замороженной квантованной базы (особенно ценно на слабом железе), чекпоинты в safetensors.

## 15. Форматы моделей и безопасность

| Формат | Назначение | Реализация |
|--------|-----------|------------|
| GGUF | квантованные LLM | парсер заголовка/метаданных, mmap тензоров, маппинг GGML-типов → ii dtype |

переполнения, никаких чтений за границами; каждый парсер (ONNX, GGUF, safetensors, `.ii`, JSON, токенизаторы,
Jinja) — под фаззингом (libFuzzer) в CI.

## 16. Встраивание и сборка

- **CMake ≥ 3.25**, `CMakePresets.json`; цели `ii::ii` (библиотека), `ii` (CLI); `find_package(ii)`,
  `add_subdirectory`, `FetchContent`, pkg-config.
- **Опции**: `II_BUILD_SHARED`, `II_BUILD_CLI`, `II_BUILD_TESTS`, `II_BUILD_BENCHMARKS`, `II_WITH_TRAINING`,
  `II_WITH_LLM`, `II_BACKEND_VULKAN|CUDA|METAL`, `II_CPU_ISAS="generic;avx2;avx512;…"`, `II_MINIMAL`.
- **Минимальная сборка** для встраиваемых систем: только инференс, только CPU, только операции, нужные заданным
  моделям (как ORT minimal build) — для контроля размера бинарника.
- **ABI**: C ABI стабилен в пределах мажорной версии; C++ API — в inline namespace `ii::v1`; символы скрыты по
  умолчанию (`-fvisibility=hidden`, явный `II_API`); в публичных заголовках нет сторонних типов (pimpl).
  C ABI решает проблему MinGW↔MSVC: DLL, собранную одним компилятором, можно использовать из другого.
- **Конфигурация без глобалов**: `Context::Options { allocator, executor (пул потоков), log_sink, cache_dir,
  plugin_paths, … }`; переменные окружения `II_*` — только как переопределения по умолчанию, документированные.
- **Платформы**: Windows (MSVC, clang-cl, MinGW), Linux (GCC, Clang; x86-64, ARM64), macOS (Apple Silicon),
  Android, iOS, WebAssembly — по мере этапов.

## 19. Стиль кода и документация

- **C++20** (concepts, `std::span`, designated initializers); без модулей C++ (тулинг незрелый).
- Именование: типы `PascalCase`, функции и переменные `snake_case`, константы `kPascalCase`, файлы `snake_case.hpp/.cpp`.

- Без RTTI-зависимостей и без исключений в ядре; владение — `std::unique_ptr` / интрузивные счётчики для буферов.
- Документация API — Doxygen-комментарии `///` в публичных заголовках; концептуальная документация — `docs/`:
  архитектура, руководства («как добавить операцию», «как добавить бэкэнд», «как добавить архитектуру LLM»,
  «как писать ядро», «тюнинг производительности»), ADR на каждое существенное решение.
- Примеры в `examples/` собираются и запускаются в CI — документация не устаревает молча.
