# Building ii

ii uses CMake (≥ 3.25) with presets. Every preset is a complete, reproducible configuration; CI runs exactly the same
presets (see [ci.md](../ci.md)).

## Requirements

| Platform | Compilers | Tools |
|----------|-----------|-------|
| Windows | MSVC 2022 (17.8+), clang-cl, MinGW-w64 GCC 13+ / Clang 17+ | CMake, Ninja |
| Linux | GCC 13+, Clang 17+ (with libstdc++ 13+) | CMake, Ninja |
| macOS 13.3+ | Apple Clang (Xcode 15+) | CMake, Ninja |

Known compiler problems: GCC 14.2 for aarch64 (Ubuntu 24.04's `g++-14`) crashes with an internal compiler error on
the parameterized tests of `tests/unit/backends/cpu_backend_test.cpp` (the library builds); use GCC 13 or Clang there.
With clang-cl, use the one installed with Visual Studio (`VC\Tools\Llvm\x64\bin`): a standalone LLVM may be older
than the Visual Studio STL requires.

The library itself has no third-party dependencies. Tests and benchmarks download GoogleTest and Google Benchmark
(pinned versions, verified by SHA-256) unless `II_USE_SYSTEM_DEPS=ON`.

## Quick start

```sh
cmake --list-presets                              # presets available on this machine
cmake --workflow --preset linux-gcc-release       # configure + build + test in one step
./build/linux-gcc/bin/Release/ii info --roofline
```

Step by step:

```sh
cmake --preset linux-gcc                          # configure (Ninja Multi-Config: Debug, Release, RelWithDebInfo)
cmake --build --preset linux-gcc-release          # build one configuration
ctest --preset linux-gcc-release                  # run the tests
```

Build trees live in `build/<configure-preset>/`, binaries in `build/<configure-preset>/bin/<Config>/`.

### Windows

MSVC and clang-cl presets must run in a Visual Studio developer environment:

```bat
"C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvars64.bat"
cmake --workflow --preset windows-msvc-release
```

MinGW presets (`windows-mingw-gcc`, `windows-mingw-clang`) only need the MinGW `bin` directory on `PATH`.

## Presets

| Configure preset | Toolchain | Notes |
|------------------|-----------|-------|
| `windows-msvc` | MSVC | |
| `windows-msvc-shared` | MSVC | ii as a DLL |
| `windows-msvc-asan` | MSVC | AddressSanitizer |
| `windows-clang-cl` | clang-cl | |
| `windows-mingw-gcc`, `windows-mingw-clang` | MinGW-w64 | |
| `linux-gcc`, `linux-clang` | GCC, Clang | |
| `linux-gcc-shared` | GCC | ii as a shared library |
| `linux-clang-asan` | Clang | AddressSanitizer + UndefinedBehaviorSanitizer |
| `linux-clang-tsan` | Clang | ThreadSanitizer |
| `macos-clang` | Apple Clang | deployment target macOS 13.3 |

Build, test and workflow presets are named `<configure-preset>-<config>`, e.g. `linux-gcc-debug`.
Presets are generated by `scripts/generate_presets.py`; edit the script, not `CMakePresets.json`.

## CMake options

| Option | Default | Meaning |
|--------|---------|---------|
| `II_BUILD_SHARED` | `OFF` | Build `ii` as a shared library |
| `II_BUILD_CLI` | top-level | Build the `ii` command-line tool |
| `II_BUILD_TESTS` | top-level | Build tests |
| `II_BUILD_BENCHMARKS` | top-level | Build benchmarks |
| `II_INSTALL` | top-level | Generate install rules |
| `II_WARNINGS_AS_ERRORS` | `OFF` (`ON` in presets) | Treat warnings as errors |
| `II_SANITIZE` | empty | `address;undefined`, `thread` (GCC/Clang) or `address` (MSVC) |
| `II_CPU_ISAS` | `auto` | Kernel ISA variants to compile, e.g. `generic;avx2` |
| `II_USE_SYSTEM_DEPS` | `OFF` | Use installed GoogleTest / Google Benchmark |

## Using ii from another project

As a subdirectory or with FetchContent:

```cmake
add_subdirectory(third_party/ii)   # or FetchContent_MakeAvailable(ii)
target_link_libraries(my_app PRIVATE ii::ii)
```

As an installed package:

```sh
cmake --install build/linux-gcc --config Release --prefix /opt/ii
```

```cmake
find_package(ii 0.1 REQUIRED)
target_link_libraries(my_app PRIVATE ii::ii)
```

A `ii.pc` file is installed for pkg-config users.

## Testing every kernel variant on one machine

CPU kernels are compiled for several instruction sets and the best supported one is chosen at runtime. To exercise a
specific variant, force it with `II_CPU_ISA`:

```sh
II_CPU_ISA=generic ctest --preset linux-gcc-release
```

The ii-cpu tests also iterate over every variant the CPU supports by themselves. Variants the CPU lacks (e.g. AVX-512
on most desktops) can be tested under [Intel SDE](https://www.intel.com/content/www/us/en/developer/articles/tool/software-development-emulator.html):
`sde64 -spr -- ii_tests --gtest_filter='Isa/*'`.

`ii info` lists the compiled variants and which of them the CPU supports.

## Testing multi-device plans without a GPU

`II_TEST_DEVICES` adds simulated devices (the `ii-test-remote` backend) to every context, so any test or tool runs
on mixed host/device plans with transfers between them:

```sh
II_TEST_DEVICES="launch=0,latency=0,link=100000,gflops=100000,bandwidth=100000" ctest --preset linux-gcc-release
II_TEST_DEVICES="memory=250M,gflops=20000,bandwidth=800" ii inspect model.gguf --plan --ctx 256
```

The first device takes every operation it can; the second is a realistic one with 250 MB of memory, so a larger
model is split between it and the CPU. Keys: [testing-and-benchmarks.md](../testing-and-benchmarks.md) §2.3.

With tests enabled, the same device is also built as a backend plugin into `build/<preset>/plugins/<config>`. Put
that directory on `II_PLUGIN_PATH` to take the devices from the plugin instead (the plugin can come from another
compiler's build — the interface is plain C):

```sh
II_PLUGIN_PATH=build/linux-gcc/plugins/Release II_TEST_DEVICES=default ctest --preset linux-gcc-release
II_TEST_DEVICES=default ii check-backends --plugin build/linux-gcc/plugins/Release
```

Writing plugins: [backend-plugins.md](backend-plugins.md).

## The CUDA backend

The NVIDIA GPU backend `ii-cuda` is the plugin `ii-backend-cuda`, built when CMake finds the CUDA Toolkit
(`-DII_BUILD_CUDA=OFF` skips it). nvcc needs MSVC as its host compiler on Windows, so it is built by the MSVC presets
(`windows-msvc*`, not the ASan one); Linux builds it with GCC or Clang. An ii built with MinGW or clang-cl uses the
plugin built by MSVC: the interface between them is plain C.

```bat
rem a Visual Studio developer prompt (vcvars64.bat), CUDA 12.x or 13.x on PATH
cmake --preset windows-msvc
cmake --build build/windows-msvc --config Release
set II_PLUGIN_PATH=%CD%\build\windows-msvc\plugins\Release
build\windows-msvc\bin\Release\ii info
build\windows-msvc\bin\Release\ii check-backends --backends ii-cuda
build\windows-msvc\bin\Release\ii bench model.onnx
```

`ii bench` keeps inputs in page-locked host memory by default (copied to the GPU at full speed, like `trtexec`'s);
`--memory device` keeps inputs and outputs in GPU memory (the time of the model alone), `--memory host` in ordinary
memory.

Kernels are compiled for `CMAKE_CUDA_ARCHITECTURES` (default `75-virtual;86-real;89-real;120-real`; `native` builds
for the GPU of the build machine only, which is faster). At run time the plugin needs an NVIDIA driver, cuBLASLt and
NVRTC of the toolkit's major version; it finds them in the plugin option `cuda.library_path`, next to the plugin, in
`CUDA_PATH`, in the toolkit it was built with and on the system's library path (CUDA 13 on Windows keeps its DLLs in
`bin\x64`, which the plugin also searches). Without them `ii info` lists the plugin as unavailable with the reason.

Options (`ContextOptions::plugin_options` or `II_PLUGIN_OPTIONS=key=value;key=value`):

| Option | Meaning |
|--------|---------|
| `cuda.devices` | `all` (default), device indices (`0,2`) or `none` |
| `cuda.tf32` | `1`: f32 matrix products and convolutions may use TF32 tensor cores (faster, ~1e-3 relative error) |
| `cuda.library_path` | a directory with cuBLASLt and NVRTC, searched first |
| `cuda.prefer` | `1`: the device reports itself so fast that the planner gives it everything it supports (tests) |
| `cuda.graphs` | `0`: no CUDA graphs (repeated runs are otherwise recorded once and replayed) |
| `cuda.autotune` | `0`: no measurements (cuBLASLt's first algorithm, default kernel parameters, nominal device figures) |
| `cuda.cache` | the autotuning cache file; default `cuda-<device uuid>.json` in ii's cache directory (`II_CACHE_DIR`, `%LOCALAPPDATA%\ii\cache`, `$XDG_CACHE_HOME/ii`); `none`: in memory only |
| `tensorrt.devices` | `all` (default), indices such as `0,2`, or `none` |
| `tensorrt.library_path` | a directory with `nvinfer_10.dll` / `libnvinfer.so.10` (searched before `TENSORRT_ROOT`, the TensorRT the plugin was built with and the system path) |
| `tensorrt.tf32` | `1`: f32 products may use TF32 tensor cores |
| `tensorrt.prefer` | `1`: TensorRT gets every part of the GPU's work it can compile (tests) |
| `tensorrt.cache` | the engine cache directory; default `tensorrt` in ii's cache directory; `none`: no cache |
| `tensorrt.level` | TensorRT's builder optimization level, 0-5 (default 3) |
| `tensorrt.profile` | ranges of symbolic dimensions, e.g. `N=1:8:64,S=1:128:512` (min:opt:max) |

The first context on a GPU measures the device for the planner (well under a second) and later runs measure the
cuBLASLt algorithm and kernel parameters of every new product shape once; the results are kept in the cache file.
Language models run on the GPU by default: `ii generate model.gguf -p ...`, `ii bench model.gguf --llm`; with
`--device-memory cuda:0=4G` the front of the model runs on the CPU.

The TensorRT plugin `ii-backend-tensorrt` is built by the same MSVC presets when the TensorRT headers are found
(`-DII_TENSORRT_ROOT=C:/TensorRT`, the `TENSORRT_ROOT` environment variable, or `C:/TensorRT`; TensorRT 10 or newer;
`-DII_BUILD_TENSORRT=OFF` to skip). nvinfer is loaded at run time, so the plugin reports itself unavailable where
TensorRT is missing. With both plugins found, CNNs and transformer encoders become TensorRT engines and ii-cuda runs
the rest; the first run of a new model builds its engines (seconds to a minute), later runs load them from the cache.

The whole test suite can run on the GPU (every operation ii-cuda supports goes there):

```bat
set II_PLUGIN_PATH=%CD%\build\windows-msvc\plugins\Release
set II_PLUGIN_OPTIONS=cuda.prefer=1
ctest --preset windows-msvc-release
```

## Android

Install the Android NDK (r27 or newer) and point `ANDROID_NDK_HOME` at it, then use the `android-arm64` or
`android-x86_64` presets:

```sh
export ANDROID_NDK_HOME=$HOME/Android/Sdk/ndk/<version>
cmake --preset android-arm64
cmake --build --preset android-arm64-release
ctest --preset android-arm64-release     # runs on the device selected by adb (ANDROID_SERIAL)
```

The minimum API level is 26 (Android 8.0). For Android builds CMake runs every test executable through
`scripts/android_run.py`, which copies it (plus test data and other host paths it needs) to `/data/local/tmp/ii` with
`adb` and runs it there, so `ctest` works unchanged on a connected phone or an emulator. Benchmarks and the CLI run
the same way: `python scripts/android_run.py build/android-arm64/bin/Release/ii info`.

## Model tests

The CLI and `examples/yolo` decode images with stb_image (fetched like the test dependencies). Real models are
compared with ONNX Runtime by two scripts (Python with `onnxruntime`; `ultralytics` to export YOLOv8):

```sh
python scripts/fetch_models.py --cache build/models-cache --suite pr      # or nightly
python scripts/model_tests.py --cache build/models-cache --ii build/<preset>/bin/Release/ii \
    --yolo build/<preset>/bin/Release/ii_example_yolo
```

Language models are compared with transformers (Python with `torch` and `transformers`):

```sh
python scripts/fetch_models.py --cache build/models-cache --suite nightly          # GGUF files, HF directories, text
python scripts/llm_tests.py --cache build/models-cache --suite nightly --ii build/<preset>/bin/Release/ii
python scripts/compare_transformers.py logits.npz --reference <hf-dir> --text "..."  # after ii generate --save-logits
```

The tiny test models, chat template cases and other reference data are regenerated by `scripts/gen_*.py`
(see the docstring of each; they need `gguf`, `safetensors`, `transformers`).

The ONNX operator conformance suite needs the `onnx` package:

```sh
python scripts/onnx_node_tests.py --out build/onnx-node-tests
build/<preset>/bin/Release/ii_onnx_tests build/onnx-node-tests --expected tests/onnx/expected_passes.txt
```

## Benchmarks

```sh
./build/linux-gcc/bin/Release/ii_bench_micro --benchmark_filter=ParallelFor

```

Benchmark numbers are only meaningful for Release builds on an otherwise idle machine.
